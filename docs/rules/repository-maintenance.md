# Repository maintenance rules

These rules apply to contributors and coding agents working on the public Cynos
Engineer source repository.

## Repository identity

- This repository contains `@cynos-ai/engineer`, a pi extension.
- Use normal repository evidence: read files, inspect Git state, edit deliberately,
  and run the public npm verification commands.
- Do not assume the installed extension is managing this checkout.

## Public/private boundary

- `docs/` contains public documentation only.
- Maintainer experiments, private benchmark data, smoke transcripts, personal
  configuration, and internal design history belong outside this repository.
- Do not commit `.cynos/` work state, screenshots, generated bundles, tarballs,
  `node_modules/`, credentials, or machine-specific paths.
- Keep all configuration examples free of real secrets.

## Runtime changes

- Preserve the core model: a practice combines methodology and completion
  checkpoints; captured tool results prove observable actions.
- Do not replace captured evidence with agent prose.
- Capability integrations must remain separable from work-state validation.
- Changes to a practice should update its skill, evidence schema, checkpoints,
  tests, and public documentation when applicable.

## Packaging and release

- `index.js` is generated by `scripts/build.mjs` and is ignored by Git.
- The build output is a readable, unminified esbuild bundle.
- `npm run pack:dry-run` is required for package, README, skill, subagent, license,
  and release metadata changes.
- Keep package contents intentional. Repository-only directories such as
  `extensions/`, `scripts/`, `docs/`, `.github/`, and `tests/` must not enter the
  npm tarball.
- Keep `package.json`, `package-lock.json`, `LICENSE`, README license text, and
  third-party notices consistent.

## Verification

Before handoff, run:

```bash
npm run verify
npm run pack:dry-run
```

For security-sensitive changes also run a repository secret scan and
`npm audit --omit=dev`.
